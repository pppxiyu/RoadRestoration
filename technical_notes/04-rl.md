# 04 — RL solver: 以 flow 为锚的 DQN 在修复顺序空间中的搜索

本笔记覆盖 `util/rl.py` 的强化学习求解器,入口是 `run_rl`(util/rl.py:567)。它与 note 03 的 GA、PSO 处在完全相同的位置上,也就是在"修复优先顺序"空间里搜索,并用同一个真实评估器打分;不同之处在于它不靠种群重组,而是靠一个从 flow 基线出发、边采样边学习的动作价值函数来引导搜索。诊断图的绘制在 `viz/rl_viz.py`。问题设定、目标函数 $`F`$ 的完整定义以及 work-conserving 排程归约见 note 01 的 Step 1 与 Step 3,本笔记只在用到处简述。

---

## Overview

### 1 · Problem

在 note 02 与 note 03 的结果里,交替 MILP 依赖冻结流量的线性代理,损毁越重代理越失真,而 GA 与 PSO 直接对真实目标搜索,却把每次评估都当作孤立样本,评估之间不积累任何可迁移的知识。这一步要回答的问题是,能否用一个学习到的价值函数把已花费的评估利用起来,在与 GA、PSO 相同的搜索空间和相同的算力上限之内,既不引入任何目标代理,又不比最强的静态基线差。

### 2 · Approach

求解器是一个逐 scenario 独立训练的 DQN。每个 episode 从空排程出发,每当有施工队空闲就在"尚未派工"的路段中选一段,凑满一个完整修复顺序后交给真实评估器打分;动作价值网络以 flow 基线的打分作为固定先验,学习部分只输出对先验的修正。训练没有任何预训练阶段,也没有教师轨迹,唯一的先验知识以权重构造的方式植入(util/rl.py:14-21)。

两条保证在进入细节之前先说清楚,因为它们不依赖训练是否收敛:

- **不差于 flow 基线,逐 scenario 成立。** 它由两个事实拼成,其一是第 0 个 episode 被强制贪心,而此时网络的可学习部分恒为零,贪心顺序逐位复现 flow 顺序(Step 2 与 Step 3 给出机制);其二是最终交付取全程真实 $`F`$ 最低的排程,而 flow 的排程恰好是第 0 个被记录的候选(Step 8)。两者都与学习质量无关。
- **与 GA、PSO 严格可比。** 三者搜索同一个排列空间,共用同一个 work-conserving 归约与同一个评估器,唯一评估次数受同一个上限 `BUDGET_CAP` 约束(util/rl.py:131-134),因此横向比较不需要任何换算。

### 3 · Interpretation · 为什么无代理这一点在这个项目里特别重要?

要回答的疑问是,为什么“不经过任何目标代理”这一性质在这个项目里值得单独强调。note 02 的跨损毁结论表明,冻结流量代理在 42% 损毁及以上把 MILP 引向比 flow 更差的排程,方向性完全失效。这里的 RL 奖励直接从真实评估器的逐时隙输出中切出(Step 5),不存在"代理随非线性增强而失真"这条失败通道;它付出的代价是每个新排程都要付一次完整评估,所以它与 MILP 的比较本质上是"贵而真"与"便宜而假"的比较,而与 GA、PSO 的比较才是同价位的公平竞争。

### 4 · Interpretation · 逐 scenario 独立训练放弃了什么?

要回答的疑问是,为什么不训练一个跨 scenario 共享的网络。每个 scenario 的修复时长实现不同,最优顺序也不同,共享网络需要在十个各自确定性的解之间折中,存在被平均化的风险;而独立训练把 RL 摆到与 GA、PSO 完全相同的"单实例搜索器"位置上,比较结论最干净。放弃的是跨 scenario 的泛化红利,这是当前阶段有意的取舍,代码中每个 scenario 使用独立的网络、独立的回放缓冲与独立的随机数流(util/rl.py:402-405)。

## Step 1 · 共享实例的准备与 scenario 级并行

### 1 · Problem

十个 scenario 的训练彼此独立,但它们共享同一份损毁实例、同一个 horizon 与同一份 flow 先验,这一步要把共享部分一次算好,并把互不依赖的训练分发到并行进程上。

### 2 · Approach

`run_rl` 先用与其他求解器相同的入口取得损毁实例、时长 scenario 集合与 horizon(util/rl.py:586-589),再解一次完好路网的 user equilibrium 得到每段的双向基线流量,作为 flow 先验的原始分数(util/rl.py:590)。随后按"每个待训 scenario 一个进程"开进程池,worker 在初始化时各自构建一次评估上下文(util/rl.py:612-613, 539-545)。已经出现在 `rl_optima.csv` 里的 scenario 在重启时直接跳过,训练轨迹按同一份完成清单过滤,避免重训 scenario 的旧轨迹与新轨迹交错(util/rl.py:594-605)。

这一步里所有 user equilibrium 求解都把交通分配引擎钉在单核上。原因是引擎的多线程归约顺序不稳定,同一输入两次求解会留下约 1e-10 量级的流量噪声;对其他求解器无害,但这里的贪心 argmax 会把如此微小的噪声放大成完全不同的排程,单核钉死后同一个种子可以逐位复现整次运行(util/rl.py:60-65)。

### 3 · Interpretation · 为什么并行的单位是 scenario 而不是评估?

要回答的疑问是,GA 与 PSO 都在 scenario 内部并行评估种群,RL 为什么不这样做。原因是 RL 的评估序列本质上是串行的,第 $`k`$ 个 episode 提出什么排程取决于前 $`k-1`$ 个 episode 训练出的网络,种群式的批量并行不存在;于是唯一可用的并行维度就是 scenario 之间,十个进程各自串行训练,墙钟约等于最慢的那个 scenario。

## Step 2 · 残差形式的动作价值网络,以及 flow 先验的植入方式

### 1 · Problem

网络要在候选集合不断收缩的情况下为任意子集里的路段打分,还要保证在训练开始之前,它的贪心行为就精确等于 flow 基线,而不是从随机策略起步。

### 2 · Approach

动作价值函数取打分器形式,每次前向输入一个(状态,候选段)对,输出一个标量,决策时对当前所有候选各算一次再取最大。写成公式(记号与源码一致,`prior_scale` 记为 $`c`$),

```math
Q(s,e) \;=\; c\,\hat\phi_e \;+\; h\big(x(s,e)\big)
```

- $`Q(s,e)`$ 是在状态 $`s`$ 下把路段 $`e`$ 派给当前空闲施工队之后,预计还能获得的奖励总和;
- $`\hat\phi_e`$ 是路段 $`e`$ 的灾前双向均衡流量除以受损集合内的最大值,取值落在 0 到 1 之间,与静态 flow greedy 用来排序的分数同源(util/rl.py:276);
- $`c`$ 是先验权重,当前取 0.82,它把先验的量级缩放到与学习到的价值可比的范围(util/rl.py:114-115);
- $`h`$ 是唯一可学习的部分,一个 8 维输入、单隐层 16 个 tanh 单元、线性单输出的小型多层感知机,前向、反向与 Adam 更新全部以 numpy 手写,不引入深度学习框架依赖(util/rl.py:202-252);
- $`x(s,e)`$ 是 8 维特征向量,前四维是候选段自身的属性,即归一化的先验分 $`\hat\phi_e`$、severity、修复时长与可释放需求,后四维是全局状态,即时间进度、另一支施工队还需忙碌的时长、当前被压制的需求占比与剩余工作量占比,全部归一到大致 0 到 1 的范围(util/rl.py:284-300)。

先验的植入靠一次权重构造。隐层用 Xavier 均匀初始化,而输出层的权重与偏置被显式置为精确零(util/rl.py:213-214),因此初始时 $`h`$ 恒等于零,$`Q`$ 退化为 $`c\,\hat\phi_e`$,对候选取最大就是对 flow 分数取最大。skip 一侧不参与任何梯度更新,它只是把特征矩阵的第 0 列乘以 $`c`$ 加到网络输出上(util/rl.py:303-307)。

### 3 · Interpretation · 为什么用打分器而不是固定维数的输出头?

要回答的疑问是,DQN 的常见形态是一个状态映射到全体动作的价值向量,这里为什么不用。因为候选集合每派一段就缩小一格,固定维数的输出头必须配合动作掩码把非法动作的输出压到负无穷,多出一处容易出错的机制;打分器的输出维数与候选数无关,候选集合怎样收缩网络结构都不变,换问题规模也无需改动网络。合法性因此不靠惩罚或掩码,而是由 Step 3 的候选集合构造直接保证。

### 4 · Interpretation · 这个先验是锚还是初始条件?

要回答的疑问是,把 $`\hat\phi_e`$ 同时放进 skip 与特征第 0 列,先验是否真的不可抹除。诚实的回答是不能保证。网络在特征里能看到 $`\hat\phi_e`$,原则上可以学出恰好抵消 skip 的修正,把先验的排序信息完全清除;在旧的窗口式奖励下这曾被诊断性实验实际观测到。因此严格地说,这个构造保证的只是第 0 个 episode 的行为,先验此后是被精化还是被冲掉,取决于奖励信号的质量,这也是 Step 5 的奖励设计如此重要的原因。Caveat C3 记录这一残留风险。

## Step 3 · 一个 episode 的展开,合法性由候选集合的构造保证

### 1 · Problem

策略要一步步把完整修复顺序拼出来,期间不能重复派同一段、不能超过施工队数量,还要让状态特征的计算不花费任何 user equilibrium 求解,否则光是"看状态"就会吃掉算力预算。

### 2 · Approach

rollout 维护一个按边号升序排列的"尚未派工"列表。每当某支施工队空闲,就对列表中每个候选构建特征行,以概率 $`\varepsilon`$ 均匀抽一个,否则取价值最大的一个,选中的段立即从列表中弹出并派给最早空闲的施工队(util/rl.py:331-355)。因为特征矩阵只为列表内的段构建,argmax 与随机抽取都只在这张矩阵上进行,重复修复同一段这件事在输入端就无法表达,不需要任何惩罚或修复步骤;循环恰好执行段数次,每段被派且只被派一次。施工队分配的规则与 `schedule_from_permutation` 的 work-conserving 归约逐句一致,所以 rollout 产出的开工时刻表与其他求解器的完全同构。

状态特征中唯一随时间演化的量是需求缺口,它的递推只依赖损毁轨迹,不需要交通分配,rollout 在两个决策点之间把缺口递推逐时隙推进到当前时刻(util/rl.py:333-343),因此整个 episode 的决策过程零 user equilibrium 成本,评估只在排程完整之后发生一次。

并列时取最大的规则是"第一个最大值",而候选按边号升序,所以并列取最小边号,与 note 03 静态 greedy 的排序规则完全一致(util/rl.py:349)。第 0 个 episode 被强制取 $`\varepsilon = 0`$(util/rl.py:457-459),配合 Step 2 的零初始化,它的输出逐位等于 flow 顺序,这一点在 $`n=10`$ 的十个 scenario 上与 `flow_optima.csv` 对照验证到 1e-12 精度(viz/rl_viz.py:103-105)。此后 $`\varepsilon`$ 从 0.2 起按每 episode 乘 0.98 衰减,下限 0.10(util/rl.py:117-120)。

### 3 · Interpretation · 探索调度为什么起点低、衰减慢、下限高?

要回答的疑问是,这组数值与常见的"高起点快衰减"相反,为什么。它是调参在新奖励下选出的形态,直觉上与奖励的归因质量相符,当每个动作的功劳都能被直接记账时,持续的中等探索比早期猛烈探索更有价值,因为任何时刻发现的改进都能被正确归因并立即吸收;相反在归因模糊的奖励下,后期探索的样本无法转化为定向的改进,只能靠前期广撒网。这一解释是事后的直觉性说明,当前唯一的硬证据是两阶段调参在三个 scenario 与两个种子上的均值排序(util/rl.py:96-103)。

## Step 4 · 唯一评估记账与前缀缓存的真实评估

### 1 · Problem

评估一个排程要在 horizon 的每个时隙各解一次 user equilibrium,是全流程唯一昂贵的操作。搜索既要保证同一排程绝不付两次钱,也应当利用不同排程之间共享的结构少付一些,但省钱不能改变任何数值。

### 2 · Approach

以排列为键的备忘录保证每个排程至多真实评估一次,重复提出的排程直接取回历史结果,不消耗唯一评估计数(util/rl.py:464-468)。真正的评估走 `_evaluate_prefix_cached`,它把 `evaluate_schedule` 的逐时隙循环逐句重述,唯一的增改是给每个时隙的不便度 $`g_t`$ 配一个缓存键。这里 $`g_t`$ 指第 $`t`$ 个时隙上,以当期需求加权的实际出行时间与灾前出行时间之比,horizon 内 $`T`$ 个时隙的均值就是目标 $`F`$ 的可达性项,完整定义见 note 01。缓存键之所以可行,是因为 $`g_t`$ 由截至 $`t`$ 的损毁轨迹唯一决定,需求缺口的记忆性使得整个前缀而非仅当期状态才是充分信息;键因此编码为每段完工时隙在 $`t+1`$ 处截断的向量,截断在 $`t+1`$ 而不是 $`t`$,是为了让"恰在 $`t`$ 完工"与"在 $`t`$ 仍损毁"保持可区分(util/rl.py:146-151, 173)。两个排程只要前若干时隙的损毁轨迹一致,就共享那些时隙的求解结果,而 $`\varepsilon`$-greedy 恰好倾向于保留头部、扰动尾部,所以命中率可观,生产运行在 $`n=10`$ 上实测省去约四分之一的求解。

缓存只省墙钟不改数值,这一等价性有验证套件逐项对照过,函数的文档串明确要求任何数值性改动都必须保持该等价(util/rl.py:153-155)。评估内部的交通分配同样钉单核(util/rl.py:177-179)。

### 3 · Interpretation · 记账口径为什么用唯一评估数而不用实测求解数?

要回答的疑问是,预算若按实测 user equilibrium 次数计,前缀缓存省下的钱就能换更多评估,为什么不这样做。因为预算的意义是与 GA、PSO 的可比性,它们的口径是唯一评估次数,RL 若按实测次数记账就等于变相多拿预算。于是预算仍按唯一评估数收紧,而对比图的算力横轴反其道而行,取实测求解数,理由是那张图要回答的是"实际花了多少算力",用上界会高估 RL 的开销;两个口径各司其职,都不会把 RL 算便宜。

## Step 5 · 完工归因的奖励,从已评估轨迹中零成本切出

### 1 · Problem

奖励要把功劳记到具体路段头上。早先的设计把决策点之间流逝时隙的不便度记给当次决策,但那段窗口反映的是更早决策造成的路网状态,所选路段的效果要等它完工才显现,功劳只能靠价值自举链条隔多步回传;诊断实验证实这种奖励下策略并没有变好,好成绩全靠采样运气加最优保底。这一步要让"修这条路带来的改善"直接成为这条路的奖励,同时不为此多付任何 user equilibrium 求解。

### 2 · Approach

排程评估完成后,逐时隙不便度序列已经在手。路段 $`e`$ 在时隙 $`\tau_e`$ 完工,$`\tau_e`$ 是它开工时隙与修复时长之和,也是它恢复通行的第一个时隙,于是跨越完工边界的两个相邻时隙恰好夹出这次修复造成的变化(util/rl.py:366-370, 393),

```math
\delta_e \;=\; g_{\tau_e - 1} \;-\; g_{\tau_e}
```

- $`\delta_e`$ 是完工瞬间目标的改善量,不便度下降为正,修复有益时它是正数;
- $`g_{\tau_e - 1}`$ 与 $`g_{\tau_e}`$ 分别是完工前最后一个时隙与完工后第一个时隙的不便度,含义与 Step 4 相同,两者都来自已经算完的轨迹,归因不花一次新求解。

这份改善不会永久保留。损毁曾压制一部分出行需求,修复后被压制的需求按系数 $`\rho`$ 逐时隙回流,车流回升重新造成拥堵,吃掉一部分改善;奖励因此取跳变加上按同一系数几何衰减的回声,对剩余时隙求和(util/rl.py:372-376, 394),

```math
R \;=\; \delta_e \sum_{j=0}^{T-\tau_e} \rho^{\,j} \;=\; \delta_e\,\frac{1-\rho^{\,T-\tau_e+1}}{1-\rho}
```

- $`R`$ 是调度了路段 $`e`$ 的那次决策获得的全部奖励;
- $`\rho`$ 是需求模型的回流系数,当前取 0.7,衰减速率直接取自需求模型本身而不是新造的超参数,因为吃掉改善的机制就是需求回流;
- 求和上限 $`T-\tau_e`$ 是完工后剩余的时隙数,$`T`$ 是 horizon 长度,完工越早享受改善的时间越长,几何和越大,这正是智能体需要的"早修关键路段"的排序激励。

两段路在同一时隙完工时,跳变是一个联合量,按两段路灾前正常期流量 $`\phi_e`$ 的比例拆分(util/rl.py:379-381, 395-398)。奖励算出后,转移按完工时隙排序进入回放缓冲,而不是按决策顺序,因为一次决策的奖励要等它的路段完工才可观测,而完工顺序不等于决策顺序;按揭示顺序入库使缓冲的任意前缀都只含奖励已揭示的转移(util/rl.py:475-482)。

### 3 · Interpretation · 它与 Babaee et al. (2026) 的反事实奖励是什么关系?

要回答的疑问是,文献中已有的逐路归因奖励为什么不直接采用。Babaee 的奖励把"修了这组路"与"不修"两条轨迹在剩余 horizon 上的总成本之差记给该决策,反事实一侧要求重新模拟整条尾段交通演化,每次奖励多付一整条轨迹的代价,并且其反事实假设其余损毁路段在尾段内全程不变,本质上与 note 02 的冻结代理同族。这里的设计把反事实压缩为"完工前最后一个时隙"这一个点,再用需求模型自己的回流速率外推尾段,归因语义保持,增量成本为零;代价是外推只是趋势近似,单时隙跳变里还混入了当隙的需求漂移。这个近似的伤害有限,原因在于奖励只承担学习信号的职责,最终交付始终由真实 $`F`$ 挑选,Caveat C1 展开这一点。

### 4 · Interpretation · 奖励之和不再等于目标,为什么可以接受?

要回答的疑问是,旧奖励曾精确满足"回报等于目标改善",新奖励放弃了这一恒等式,是否危险。恒等式的价值在于让"最大化回报"与"最小化 $`F`$"在数学上重合,但诊断表明它是以归因质量为代价换来的,而归因失效时学习者实际上退化为随机采样,恒等式徒有其表。放弃之后,学习者优化的是一个与目标近似对齐的塑形量,输出质量则完全不依赖该近似,由 flow 起点加最优保底双重兜住;在最差 scenario 上的对照实验里,新奖励把逐 episode 目标从无趋势翻为显著下降,证实这笔交换是划算的。

## Step 6 · DQN 更新,无折扣的 Bellman 回归

### 1 · Problem

每个 episode 产出的转移要转化为对动作价值网络的改进,并且更新要稳定,不能让自举目标追着自己跑。

### 2 · Approach

每个 episode 结束后执行 60 步小批量梯度更新,每步从回放缓冲均匀抽 16 条转移,回归目标按 Bellman 方程构造(util/rl.py:484-498),

```math
y \;=\; R \;+\; \max_{e' \in U'} Q^{-}(s', e')
```

- $`y`$ 是这条转移的回归目标;
- $`R`$ 是 Step 5 定义的该转移奖励;
- $`s'`$ 与 $`U'`$ 分别是下一个决策点的状态与彼时的候选集合,最大值只在合法候选上取,自举不会流经已修复的路段,末次决策没有后继项,目标退化为 $`R`$ 本身(util/rl.py:491-493);
- $`Q^{-}`$ 是目标网络,即主网络参数的延迟拷贝,每 25 步梯度更新同步一次,用来稳住回归目标(util/rl.py:500-501)。

损失取均方误差,梯度只流入可学习的修正部分,skip 一侧视为常数;优化器是手写的 Adam(util/rl.py:494-498)。折扣固定为 1 且不参与调参,原因是有限 horizon 的时间衰减已经由奖励自身的 $`\rho`$ 回声承载,再叠加一层折扣就会对同一效应重复贴现(util/rl.py:110-111)。每步小批量的平均绝对 Bellman 残差被记录进训练轨迹,作为"学习本身是否收敛"的诊断量(util/rl.py:486, 496)。

重复提出已评估排程的 episode 同样执行这 60 步更新,它们的奖励从备忘录免费取回,等于用零算力继续消化已有经验(util/rl.py:464-465)。

## Step 7 · 贪心探针与三条件走平终止

### 1 · Problem

训练应当在优化明显走平时停下,而不是在花完某个任意数额的算力时停下。难点是"走平"的判据,单一信号在这个问题上会系统性误判。

### 2 · Approach

每个 episode 的更新结束后,额外做一次强制贪心的 rollout,只取它的顺序、不做评估,因此零 user equilibrium 成本;连续多少个 episode 该顺序保持不变,就是策略稳定性的计数(util/rl.py:503-507)。训练循环在每轮开头检查三个条件,全部满足才停(util/rl.py:453-456, 124-128):

- episode 数不少于 45。这一条存在的原因是,在探索仍强时不应判定走平;按当前调度,探索率 $`0.2 	imes 0.98^{\,k-1}`$($`k`$ 为 episode 序号)首次触及下限 0.10 发生在第 36 个 episode(util/rl.py:117-119),45 在这之后留有余量。参数注释里写的约 41 个沿自旧的探索调度,记入 C4;
- 贪心顺序连续 15 个 episode 不变,即策略侧已经稳定;
- 最优真实 $`F`$ 连续 30 个 episode 无改进,即搜索侧也已经停滞。

两个走平信号缺一不可的原因写在训练函数的文档串里(util/rl.py:417-423)。最优值的改进在这个问题上呈稀疏突发,设计时的 $`n=10`$ 运行里两次改进之间的最长空档达到 55 个 episode,而整轮不过 66 到 97 个,单靠无改进耐心会在拿到最终改进之前截断;反过来,贪心顺序稳定是每期可测的平滑信号,但它单独成立时可能只是策略陷入僵局而探索仍在产出更好的排程。两者同时要求,训练恰好在"策略和搜索都还在动"的整个期间保持存活。此外还有两道纯粹的安全网,唯一评估数的上限 `BUDGET_CAP` 与 episode 数上限,越先触发者生效(util/rl.py:453, 128)。

### 3 · Interpretation · 在预算 60 之内这套规则实际起作用吗?

要回答的疑问是,生产配置下走平规则是否真的决定停止时机。当前不是。$`n=10`$ 的生产运行里十个 scenario 全部以耗尽 60 次唯一评估告终,走平三条件从未同时满足,调参的 28 组配置里也只有 2 组提前停止。这套规则的真正用途是在放开预算的实验里让算力成为运行的结果而非输入,当前预算下它只是兜底;这也意味着记录在结果里的停止原因字段(util/rl.py:524-525)在解读时要先看预算设置。

## Step 8 · 交付、落盘顺序与四张诊断图

### 1 · Problem

训练结束后要交付与其他求解器同构的结果行,并把训练过程的内部量落盘成可复查的诊断;落盘本身还要能安全地被中断与恢复。

### 2 · Approach

交付的排程取全程真实 $`F`$ 最低的那个,而不是末态策略的贪心输出,配合第 0 个 episode 即 flow 这一事实,交付不差于 flow 的保证在此闭合(util/rl.py:518-527)。结果行沿用 note 03 的 schema 并追加三列,分别是 episode 总数、实测 user equilibrium 求解总数与停止原因;结果文件写入 `outputs/greedy/n{N}/rl_optima.csv`,与静态 greedy 和 GA、PSO 同目录,`util/compare.py` 的通配发现机制无需改动即可纳入(util/rl.py:53-54)。对比图的算力横轴对 RL 读取实测求解数而非上界,Step 4 的第 3 小节已说明两种口径的分工。

每个 scenario 完成即落盘一次,顺序是先训练轨迹后结果行,这样若在两次写入之间被杀,留下的是"有轨迹无结果"的 scenario,重启时的恢复过滤会把它当作未完成而重训;反过来的顺序会留下永远补不回轨迹的结果行(util/rl.py:620-625)。任何 scenario 的训练抛出异常都不会静默丢行,主进程在其余 scenario 收尾后带着失败清单大声报错,因为下游对比按 scenario 做内连接,静默缺行会让所有方法的对比范围一起缩水(util/rl.py:629-634)。

训练轨迹落盘后绘制四张诊断图(util/rl.py:641-653),各自回答一个独立的问题,建议按此顺序读:

- `rl_td_error` 回答"学习本身有没有收敛",画逐 episode 平均绝对 Bellman 残差,它下降只说明网络自洽,不说明策略变好,所以要先读它排除"根本没学动",再看后两张;
- `rl_learning` 回答"搜索找到了什么",画各 scenario 最优真实 $`F`$ 随唯一评估数的下降包络,横轴用预算口径以支撑与 GA、PSO 的等预算比较;
- `rl_objective` 回答"每个 scenario 里搜索实际经历了什么",逐 scenario 一格,画每期采样的 $`F`$、最优包络与 flow 基线水平线,虚线与粗线之间的垂直距离就是 RL 相对最强静态规则的净收益;
- `rl_reward` 回答"策略本身有没有变好",画逐 episode 回报的滚动均值,它与最优包络的区别在于回报会因坏探索而下跌,只有策略真在改进时才回升。

# Caveats

## C1 · 奖励是学习信号,不是目标本身

完工归因奖励之和不等于目标的改善量,每个跳变都被几何回声外推到剩余 horizon,彼此的覆盖区间重叠;跳变本身还混入完工当隙的需求漂移,并列完工时的流量比例拆分也是一个近似(Step 5)。所以"学习者优化的量"与"交付被评判的量"是两个近似对齐而不重合的量。交付质量不受此影响,因为最终排程由真实 $`F`$ 在全部已评估候选中挑选,但解读训练曲线时必须记住回报上升不等价于 $`F`$ 下降,两者的联系是统计性的而非恒等的。

## C2 · 超参数的证据强度有限

当前默认超参来自两阶段搜索,其胜出幅度约 0.003,小于同一配置换种子造成的约 0.012 的波动,因此它是"现有证据下的最佳选择"而非被证明的最优;调参用的三个 scenario 同时也在最终报告的十个之内,$`M=10`$($`M`$ 为 scenario 总数)的规模下没有留出集。两条限定都写在参数块的注释里(util/rl.py:105-108),引用这些数值时应一并引用限定。

## C3 · 先验的抵消通道仍然存在

flow 先验同时出现在 skip 与特征第 0 列,网络原则上能学出恰好抵消 skip 的修正,把先验排序整体清除;在旧的窗口式奖励下这曾被实际观测到,动作间价值差被压缩到先验区分度的百分之几,排序随数值噪声翻动。新奖励显著改善了策略学习的方向性,但"抵消通道是否仍在被使用"未在新奖励下复测,把 $`\hat\phi_e`$ 移出特征向量是已知的候选修复,尚未实施(Step 2 第 4 小节)。

## C4 · 源文件注释中三处描述落后于代码

源文件头部的设计说明中,"停滞卫兵 40 个 episode"与"对比算力轴按唯一评估数乘 horizon 计"两段(util/rl.py:40-43, 49-51)描述的是旧版行为,现行代码分别由 Step 7 的三条件走平规则与 Step 4 第 3 小节的实测口径取代。参数注释里 ep_min 一行所写的"约 41 个 episode 到达下限"(util/rl.py:125)同样沿自旧探索调度,按当前调度应为第 36 个 episode,见 Step 7。按本系列笔记"以当前源码为唯一事实来源"的规则,以正文所述为准;这三处不一致已另行提请修正,不在本笔记内改动代码。
